# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение репозитория

Набор скиллов для AI-агентов, работающих с проектами на платформе **1С:Элемент (XBSL/SBSL)** — язык со статической типизацией для разработки бизнес-приложений.

Во всех командах ниже `{python}` означает `python` в Windows и `python3` в macOS/Linux/WSL. Выбранный интерпретатор должен быть Python 3.10+; если сомневаешься, проверь через `{python} --version`. Выбирай команду сразу по текущей ОС, не запускай оба варианта.

## GitHub и Pull Requests

## Скиллы

### xbsl-uuid
Генерирует N UUID v4 через `{python} -c`. Вызывается другими скиллами — не напрямую пользователем.

### xbsl-init
Создаёт новый проект 1С:Элемент с нуля: `{Поставщик}/{ИмяПроекта}/Проект.yaml`, `Проект.xbsl` и `{ИмяПодсистемы}/Подсистема.yaml`. Оркестрирует `xbsl-uuid`. **Вызывается перед `xbsl-meta-add`**, если проекта ещё нет.

### xbsl-explore
Запускает `scripts/explore.py --type {Тип} --name {Имя} --root {root}`. Возвращает JSON с `suggested_path` (куда класть новый файл) и `conflict` (существующий объект с таким именем). **Вызывается перед созданием любого объекта.**

### xbsl-subsystem-add
Добавляет подсистему в существующий проект: создаёт папку и `{ИмяПодсистемы}/Подсистема.yaml`. Использует `xbsl-explore` для поиска проекта и проверки конфликта. Поддерживает параметры: `Использование`, `ВключатьВАвтоИнтерфейс`, `Представление`. **Вызывается между `xbsl-init` и `xbsl-meta-add`** при добавлении нового раздела в проект.

### xbsl-meta-add
Создаёт объект конфигурации (`.yaml` + опционально `.xbsl`). Оркестрирует xbsl-explore и xbsl-uuid. Читает спецификацию из `references/{ТипОбъекта}.md`. Поддерживаемые типы: Перечисление, Справочник, Документ, РегистрСведений, РегистрНакопления, ОбщийМодуль, Структура, ЛокализованныеСтроки, HttpСервис, ГлобальноеКлиентскоеСобытие, КлючДоступа, Отчет.

### xbsl-deploy
Управляет приложениями на платформе 1С:Предприятие.Элемент через Console API v2. `scripts/api.py` — самодостаточный HTTP-клиент (только stdlib Python 3.10+). Конфигурируется через env vars: `ELEMENT_BASE_URL`, `ELEMENT_CLIENT_ID`, `ELEMENT_CLIENT_SECRET` (обязательные), `ELEMENT_APP_ID`, `ELEMENT_PROJECT_ID`, `ELEMENT_BRANCH`, `ELEMENT_SPACE_ID` (опциональные).

### xbsl-form-info
Анализирует существующий объект конфигурации и возвращает JSON: `object_path`, `fields`, `tc`, `namespace`, `suggested_layout`, `existing_forms`. **Вызывается перед `xbsl-form-add` и `xbsl-file-add`** для получения структуры объекта.

### xbsl-form-add
Создаёт форму интерфейса (`КомпонентИнтерфейса`) — `ФормаОбъекта` и/или `ФормаСписка`. Оркестрирует xbsl-explore, xbsl-form-info и xbsl-uuid. Читает спецификацию из `references/ФормаОбъекта.md` или `references/ФормаСписка.md`.

### xbsl-form-cards
Создаёт форму списка в виде карточек (`ПроизвольныйСписок` с матричной компоновкой) для Справочников и Документов. Генерирует два файла: `ФормаСписка.yaml` и `СтрокаСписка<Объект>.yaml`. Алгоритм: dry-run (`scripts/generate.py`) → показать план → применить с флагом `--apply`. Опциональный флаг `--min-width` (250 для портретов, 400 по умолчанию).

### xbsl-form-dashboard
Создаёт главную страницу приложения (`КомпонентИнтерфейса` типа `Форма`, не ФормаОбъекта/Списка) с виджетами `СтандартнаяКарточка`. Генерирует два файла: `ГлавнаяСтраница.yaml` и (при наличии динамических данных) `ГлавнаяСтраница.xbsl` с обработчиком `ПослеСоздания`. Паттерны виджетов: P1 (KPI-счётчик), P2 (навигация), P3 (таблица), P4 (баннер), P5 (диаграмма), P6 (карусель), P7 (бенто), P8 (поиск), P9 (статика). Форма не регистрируется автоматически — нужна `НавигационнаяКоманда.ТипФормы` в панели навигации.

### xbsl-file-add
Добавляет файловые вложения (`СписокФайлов`) к существующему объекту. Паттерны: P1 — стандартные вложения через встроенный реквизит `Файлы`; P2 — одиночный файл (`ДвоичныйОбъект.Ссылка?`); P3 — категория файлов (`Массив<ДвоичныйОбъект.Ссылка>` с лимитами); P4 — несколько категорий. Оркестрирует xbsl-form-info и xbsl-uuid.

### xbsl-image-add
Добавляет одиночное изображение (`ДвоичныйОбъект.Ссылка?`) к объекту конфигурации. Паттерны: P5 — простое фото (загрузка через `ВыборФайлов`, хранится как есть); P6 — фото с серверной обработкой (ресайз и/или обрезка по кругу через `ОбрабатываемоеИзображение`). Placeholder-заглушки: `Аккаунт.svg` (аватар, профиль, сотрудник), `Файл.svg` (всё остальное). Оркестрирует xbsl-form-info, xbsl-form-add (если форма не существует) и xbsl-uuid. **НЕ для файловых вложений** — используй xbsl-file-add.

### xbsl-pattern-register
Реализует движения по регистру накопления и регистру сведений в `.xbsl`. Не создаёт объекты — только пишет код обработчика. Алгоритм: запустить `scripts/extract_meta.py` для регистра и документа → выбрать паттерн → дополнить существующий `.xbsl` файл. Паттерны РН: A1 (приход), A2 (расход), A3 (обороты), A4 (отмена проведения), A5 (два регистра), B (контроль остатков). Паттерны РС: C1 (запись/обновление), C2 (добавить без замены), C3 (удалить по фильтру), C4 (срез последних).

### xbsl-lib-connect
Подключает внешнюю библиотеку (`.xlib`) к проекту. Источники: локальный `.xlib`, папка с исходниками (`ВидПроекта: Библиотека`), GitHub/GitLab URL. Алгоритм: получить `.xlib` → загрузить в облако через `api.py upload-build` → попросить пользователя выпустить релиз в панели управления (релиз через API недоступен) → получить номер релиза → прописать в `Проект.yaml` раздел `Библиотеки` → дать рекомендации по использованию типов. Для сборки `.xlib` из исходников переиспользует `build.py --kind library` из xbsl-deploy.

### xbsl-rename
Безопасно переименовывает объект конфигурации и обновляет все ссылки на него в проекте. Алгоритм: dry-run (`scripts/rename.py --old-name X --new-name Y --root .`) → показать план → применить с флагом `--apply`. Обновляет: типы реквизитов (`Имя.Ссылка?`), формы (`ФормаОбъекта<Имя.Объект>`), ссылки на формы в `Интерфейс.*.Форма`, XBSL-код, имена файлов объекта и форм.

### xbsl-access-set
Управляет секцией `КонтрольДоступа` в объектах конфигурации. Два режима: A — сводка текущего состояния прав по всему проекту (JSON); Б — установить `ПоУмолчанию` с dry-run и подтверждением. Алгоритм: `scripts/access_state.py --root .` → показать сводку → спросить желаемое значение → dry-run → `--apply`. Поддерживаемые типы: Справочник, Документ, РегистрСведений, РегистрНакопления, HttpСервис. Явно направляет в `xbsl-pattern-rls` при `РазрешенияВычисляютсяДляКаждогоОбъекта` (exit 3).

### xbsl-pattern-rls
Реализует полный паттерн RLS (Row-Level Security) — разграничение доступа к строкам данных — для объектов конфигурации (Справочник, Документ и др.). Создаёт все артефакты за один вызов: `КлючДоступа<Имя>.yaml` + `.xbsl` с обработчиком `ПроверитьНаличиеКлючейДоступа`, обновляет `КонтрольДоступа` в YAML объекта, дописывает два обработчика в `.Объект.xbsl` (уровень 1 — доступ к таблице, уровень 2 — доступ к строкам). Паттерны: P0 — без построчной фильтрации; P1 — пользователь видит только свои записи; P2 — группа по параметру (собственный ключ + запрос); P2-б — ролевой ключ без параметров; P3 — два участника с разными правами. Запускает `scripts/rls_state.py` для компактной сводки состояния объекта (вместо ручного чтения YAML + .xbsl). Оркестрирует xbsl-uuid.

## Структура проекта 1С:Элемент

Проекты 1С:Элемент, с которыми работают скиллы, устроены так:
```
<корень>/
    <Поставщик>/
        <Проект>/
            Проект.yaml
            Проект.xbsl     # обработчики НастройкаПриложения / ОбновлениеПроекта
            <Подсистема>/
                Подсистема.yaml
                СтатусЗадачи.yaml     # объект метаданных
                СтатусЗадачи.xbsl     # методы объекта (опционально)
```

`explore.py` определяет проекты по наличию `Проект.yaml`, подсистемы — по `Подсистема.yaml`.

## Разработка скиллов

Каждый скилл — папка в `.claude/skills/` с обязательным файлом `SKILL.md`. Frontmatter:
```yaml
---
name: имя-скилла        # совпадает с именем папки, a-z0-9-
description: >          # что делает + когда вызывать (до 1024 символов)
  ...
compatibility: Requires Python 3.
---
```

Ресурсы скилла (`references/`, `scripts/`) ссылаются из SKILL.md относительными путями (`references/foo.md`), но в bash-командах используется полный путь от корня проекта (`.claude/skills/<имя>/scripts/foo.py`).

При разработке нового скилла для 1С:Элемент — ориентируйся на существующие скиллы как образец.

### XBSL-код

Перед созданием или изменением `.xbsl` обязательно прочитай
`.claude/xbsl-spec.md`. Это компактный синтаксический контракт, а не справочник API:
типы, методы платформы, аннотации и сигнатуры обработчиков сверяй через `xbsl-docs`
и профильные `references/` скилла.

### Соглашения по скриптам (`scripts/`)

- **Только stdlib Python 3.10+** — никаких pip-пакетов; скрипты должны работать без виртуального окружения.
- **JSON в stdout** — скрипты выводят результат как JSON; Claude разбирает вывод и продолжает алгоритм.
- **Лёгкий YAML-парсер** — каждый скрипт содержит функцию `get_yaml_field()` для чтения `.yaml`; внешних библиотек (PyYAML и т.п.) нет.
- **Exit-коды как сигналы** — `sys.exit(N)` передаёт скиллу специальные состояния (например, `exit(3)` в `access_state.py` = объект с RLS, перенаправить в `xbsl-pattern-rls`).

### Кроссплатформенность

Во всех командах ниже `{python}` означает `python` в Windows и `python3` в macOS/Linux/WSL. Выбранный интерпретатор должен быть Python 3.10+; если сомневаешься, проверь через `{python} --version`. Выбирай команду сразу по текущей ОС, не запускай оба варианта.

- **Запуск Python** — в инструкциях и примерах используй `{python}`, а дочерние Python-процессы запускай через `sys.executable`.
- **Пути и временные файлы** — в Python-коде используй `pathlib` и `tempfile`; не хардкодь `/tmp`, обратный слеш или прямой слеш как разделитель пути.
- **Командная оболочка** — не предполагай наличие Bash. Если shell-команда неизбежна, приводи варианты для PowerShell и POSIX либо заменяй её Python-реализацией.
- **Кодировка** — текстовые файлы открывай с явным `encoding="utf-8"`.
- **Новый Python-скилл** — добавляй точную строку из `LAUNCHER_INSTRUCTION` и slug скилла в `DIRECT_PYTHON_SKILLS` файла `tests/python_runtime_contract.py`; минимальную версию Python меняй централизованно в этом разделе, `README.md` и контрактных тестах.

### Трёхфазный workflow для изменяющих операций

Любой скилл, вносящий изменения в файлы проекта, обязан следовать схеме:

1. **Dry-run** — показать план: какие файлы будут созданы/изменены и что именно.
2. **Подтверждение** — явно запросить согласие пользователя перед применением.
3. **Apply** — применить с флагом `--apply` (или аналогичным).

Реализован в: `xbsl-form-cards`, `xbsl-rename`, `xbsl-access-set`.

## Версионирование

Формат: `{версия_платформы}.{релиз}.{багфикс}`
- `версия_платформы` — версия 1С:Предприятие.Элемент (например, `9.1`, `10.0`)
- `релиз` — порядковый номер нашего релиза в рамках данной версии платформы (0, 1, 2…)
- `багфикс` — исправления в рамках релиза (0 = первый выпуск)

Примеры: `9.1.6.0`, `9.1.6.1`, `10.0.0.0`

При выходе новой версии платформы — поддерживается только актуальная линия.
