# UI/E2E-тесты приложений 1С:Элемент через Playwright

Работай с обычным consumer-проектом пользователя. Для исполнения нужны Node.js
и `@playwright/test`; не добавляй их в репозиторий скиллов. Проверяй только уже
доступное по URL приложение: этот скилл не выполняет deploy, не вызывает cloud
API и не использует встроенный браузер AI-клиента.

## Входы и режим работы

До планирования определи:

- каталог consumer-проекта;
- проверяемый сценарий и наблюдаемые критерии приёмки;
- полный URL приложения через `ELEMENT_APP_URL`;
- обязательные роли, опорные данные и разрешённые изменения данных;
- при наличии — `ELEMENT_AUTH_STATE`, ожидаемую revision приложения,
  существующие fixtures, Page Objects и правила cleanup.

Исследуй `package.json`, lockfiles, `playwright.config.*`, тестовые каталоги,
fixtures, auth setup, reporters и naming conventions. Если Playwright уже
настроен, расширяй этот setup. Если его нет, планируй изолированный пакет
`e2e/`. При неоднозначном package manager или конфликтующих lockfiles остановись
и запроси выбор; не создавай параллельную конфигурацию.

Локальные XBSL/YAML-исходники можно читать для понимания названий и бизнес-
сценария, но они не доказывают фактическую структуру DOM.

## Обязательный workflow

1. Зафиксируй обязательные сценарии и проверяемые пользователем результаты.
2. Прочитай [authoring.md](references/authoring.md) перед созданием или
   изменением тестов и Playwright setup.
3. Покажи dry-run и остановись до явного подтверждения. В dry-run перечисли:
   файлы, зависимости, браузеры и команды; URL/роль; изменения тестовых данных;
   отдельную cleanup-операцию. Начальная просьба «создай тест» не заменяет
   подтверждение показанного плана.
4. После подтверждения измени только перечисленные файлы. Установку пакетов и
   Chromium выполняй лишь когда они явно вошли в подтверждённый dry-run.
5. Если нужна авторизация или несколько ролей, прочитай
   [authentication.md](references/authentication.md). Логин, пароль, MFA и
   CAPTCHA пользователь вводит только в headed Chromium, не в чат.
6. Перед запуском и при любом падении прочитай
   [run-and-debug.md](references/run-and-debug.md). Запускай минимальный targeted
   scope, изучай evidence и исправляй только подтверждённый дефект теста или
   locator.
7. Останови repair-цикл, когда тест прошёл, обнаружен дефект приложения,
   возник внешний blocker либо следующий шаг требует изменения application code
   или расширения согласованного scope. Не ослабляй assertion ради зелёного
   результата.

Stateful-сценарий запускай только после явного подтверждения конкретных
изменений данных. Cleanup требует отдельного подтверждения и может удалять
только точные записи, созданные текущим запуском.

## Статусы и отчёт

Для общего результата и каждого обязательного сценария возвращай независимые
поля `status` и `reason`. Допустимы только сочетания:

| Status | Reason | Когда использовать |
| --- | --- | --- |
| `PASS` | `NONE` | Все заявленные критерии сценария фактически прошли |
| `FAIL` | `APPLICATION` | Корректный тест наблюдал нарушение критерия приложением |
| `BLOCKED` | `AUTH`, `ENVIRONMENT`, `SAFETY` или `PRECONDITION` | Сценарий нельзя надёжно начать или завершить из-за внешнего blocker |
| `UNVERIFIED` | `NONE` или `TEST` | Runtime-вывод не входил в scope либо дефект теста остался неподтверждённым/неисправимым |

`TEST` сначала требует исправления и targeted rerun. Общий `PASS/NONE` возможен
только когда все обязательные сценарии имеют `PASS/NONE`; условный сценарий вне
согласованного scope на общий статус не влияет. `PASS` означает прохождение
заявленных критериев, а не «багов нет».

Итоговый отчёт должен содержать:

- общий результат и результат каждого сценария с причиной;
- фактически выполненные команды и созданные/изменённые файлы;
- пройденные и упавшие assertions;
- локальные пути к trace, screenshot и HTML report без содержимого auth state;
- исправления теста и результаты повторных запусков;
- cleanup-статус, идентификаторы оставшихся данных и ограничения проверки.

Не коммить автоматически `.auth`, `storageState`, trace, screenshot или reports
и не публикуй trace: эти артефакты могут содержать cookies и сетевые данные.
