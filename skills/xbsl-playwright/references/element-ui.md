# Особенности форм 1С:Элемент

Это подсказки для исследования, а не универсальный DOM-контракт платформы.
Подтверждай каждый locator на текущем приложении и сохраняй удачные решения
в его тестах. Не переноси в reusable skill названия, URL и ID этого приложения.

## Активная форма и команды

Различай оболочку, активную форму, dialog и popup/menu. Одинаковые «Создать»,
«Записать» или «Закрыть» могут встречаться одновременно: ограничивай locator
нужной поверхностью и проверяй уникальность. Popup может лежать вне DOM-ветки
формы; после открытия ищи его по фактически наблюдаемой роли/состоянию.

Если иконки команд не имеют роли/имени, включи `ELEMENT_INSPECT_COMMANDS=1`
в готовом inspector: он выведет короткие атрибуты видимых команд выбранной
поверхности. Начни с `data-testid`, `aria-label`, `title`, `data-component`,
а не с SVG или всего HTML. В Элементе встречаются `write-command`,
`write-and-close-command`, `form-delete-command`: это подсказки для поиска,
использовать их можно только после подтверждения текущим DOM.
Не предполагай, что save закрывает форму: запись и запись с закрытием могут
быть разными командами. Проверь фактическое состояние после действия.

Недостающая команда может находиться в дополнительном меню панели, строки
или карточки. Открывай меню конкретной поверхности и проверяй появившуюся
команду; не выбирай первое многоточие на странице.

Навигация не обязательно меняет URL: дождись новой формы/диалога и проверяй
его содержимое. Если навигация не имеет ARIA-роли, исследуй точный видимый label
и ближайший устойчивый атрибут; не выдумывай role или `aria-expanded`.
Внутренние navigation tokens не разбирай и не превращай в предполагаемые URL.

После входа или `page.goto` панель навигации может появиться раньше стартовой
формы. Дождись наблюдаемой готовности её содержимого перед первым кликом меню;
после клика — заголовка целевой формы. Видимость панели сама по себе недостаточна.
В inspector вставляй наблюдённые переходы в отмеченный блок, завершая его
ожиданием точного заголовка/содержимого цели. Не заменяй готовность паузами.
При неожиданном отсутствии label проверь язык страницы перед ремонтом locator.

## Поля, выбор и таблицы

Подпись поля не всегда является HTML label. Проверь `getByLabel`, затем роль,
placeholder или видимый контейнер поля с однозначным input. Значение после
ввода проверяй в самом поле, а после сохранения — в заново открытой записи.

Ссылочное поле может открывать список/диалог выбора. Найди точную опорную запись
по известному имени и дополнительному признаку при совпадениях; после выбора
проверь значение в исходной форме. Не заменяй выбор справочника вводом текста,
если UI не подтвердил принятие значения.

В табличной части ограничивай locator точной строкой и нужной ячейкой. Если
редактирование открывает отдельный dialog, проверь его закрытие и итог строки.
Порядок строк и видимая первая страница списка не доказывают идентичность или
отсутствие записи: используй доступный поиск/фильтр по точному маркеру.

### Числовая ячейка

Встречается структура: `table-row → table-cell → value[data-testid]`; при
редактировании внутри той же ячейки появляется `base-edit-input`. Клик по
value может перехватывать уже появившийся input. Подтверди эту связь узким DOM
и используй [element-cell.ts](../assets/element-cell.ts): контейнер ячейки →
её input → fill → Tab → выход фокуса на устойчивый заголовок → проверка числа.
Передай точную строку, testid значения, blur target и parser наблюдённой локали.

`Tab` может открыть editor следующей колонки; повторный click тогда перекрывают
его элементы. Проверенный шаблон завершает editor после каждого поля. Если
другая форма использует Enter/dialog или другую структуру, адаптируй только
этот переход по наблюдаемому UI. `parseEnUSNumber` подходит только формату en-US.
После Save и нового открытия сравни каждое проверяемое число; один общий итог
не доказывает сохранение отдельных значений.

Формулу бери из требования или подтверждённых единиц поля: `Discount` само по
себе не означает проценты. Отделяй проверку сохранения заданных значений от проверки
бизнес-формулы; неизвестную формулу отчитай как неустановленную.

## Поиск и отсутствие

Поиск может оставлять старые строки до ответа сервера. После `fill` жди
результат именно нового запроса: статус с текущим фильтром и завершённой
загрузкой либо наблюдённый UI-запрос/ответ и обновление списка. Один helper
`search(query)` для reopen, негативных проверок и cleanup возвращает ID строк
только после этой синхронизации. `count() === 0` и исчезнувший spinner могут
прочитать старую пустую выдачу.

Пример для UI с подтверждёнными статусом, query-параметром и таблицей ниже.
`observedSearchPath` и locators замени по наблюдаемому приложению. Не выдумывай
endpoint: waitForResponse только наблюдает запрос, вызванный вводом в UI.

```ts
async function search(page: Page, query: string): Promise<string[]> {
  const input = page.getByRole('searchbox', { name: 'Search documents', exact: true });
  const results = page.getByRole('region', { name: 'Search results', exact: true });
  if (await input.inputValue() === query) await input.fill('');
  const loaded = page.waitForResponse(response => {
    const url = new URL(response.url());
    return url.pathname === observedSearchPath && url.searchParams.get('q') === query
      && response.request().method() === 'GET' && response.ok();
  });
  await input.fill(query);
  await loaded;
  await expect(results).toHaveAttribute('aria-busy', 'false');
  await expect(results.getByRole('status')).toContainText(`Results for "${query}":`);
  return results.locator('tbody tr').evaluateAll(rows =>
    rows.map(row => row.querySelector('td')!.textContent!.trim()));
}
```

Если UI даёт надёжный статус с текущим запросом и признаком завершения, ожидания
ответа не требуется. Общий `/documents/` совпадает и со старой выдачей и не подходит.

Даже новая пустая выдача не доказывает отсутствие, если запрос не умеет находить
такие данные. Например, поиск даты без секунд может не находить отображаемую
дату с секундами. Перед отрицательным поиском найди известную запись **по тому
же полю и в том же формате**. Поиск контрольной записи по номеру не проверяет
формат даты. Нет подходящей контрольной записи — `UNVERIFIED/TEST` для отсутствия.

Скопируй [checked-search.mjs](../assets/checked-search.mjs):

```ts
await expectAbsentBySearch({
  known: { id: knownID, marker: knownNotesMarker },
  candidate: { marker: invalidRecord.marker },
  queryFor: record => record.marker, // В обоих случаях маркер поля Notes.
  search, // Проверенный на текущем UI helper, возвращает точные ID новой выдачи.
});
data.absent('missing-title'); // Только после успешной проверки выше.
```

Для cleanup контрольной записью может быть сама удаляемая запись: сначала
найди её точным запросом и сверь ID, затем удали, выполни тот же поиск заново
и проверь пустую новую выдачу. Дополнительная контрольная запись не нужна;
`expectAbsentBySearch` предназначен для случая с отдельной живой контрольной записью.

Если в задачу входит проверка обязательности, звёздочка не доказывает validation.
Такой негативный тест выполняет
сохранение, проверяет отказ/сообщение и отсутствие невалидной записи после
повторного поиска. Не привязывайся к точному тексту платформенной ошибки,
если пользователь не потребовал именно этот текст.

При удалении различай soft delete/архив и окончательное удаление. Исчезновение
из списка доказывает только отсутствие в этом представлении; описывай
фактически проверенное действие и остатки без обещания полного удаления.
