# Запуск и диагностика

## Статусы

Для сценария и общего результата используй независимые `status` и `reason`:

| Status | Reason | Значение |
| --- | --- | --- |
| `PASS` | `NONE` | Все обязательные критерии фактически прошли |
| `FAIL` | `APPLICATION` | Корректный тест подтвердил дефект приложения |
| `BLOCKED` | `AUTH`, `ENVIRONMENT`, `PRECONDITION`, `SAFETY` | Нет сессии, среды, опорных данных/роли или разрешения |
| `UNVERIFIED` | `NONE`, `TEST` | Проверка не запускалась или ошибка теста не разрешена |

## Запуск сохранённого теста

Проверь Node.js, локальный `@playwright/test`, Chromium, `ELEMENT_APP_URL` и
наличие необходимых auth paths. Используй существующую команду/конфигурацию;
не исследуй интерфейс заново, пока тест не показал такую необходимость.

Запускай нужный spec или точный test title через project-local executable.
Полный suite нужен для запрошенной регрессии. Для stateful-тестов —
`retries: 0`; независимые datasets не связывай в serial-группу. Зафиксируй
команду, exit code и фактические результаты обязательных тестов.

Нет runtime/браузера, URL недоступен или 5xx — `BLOCKED/ENVIRONMENT`.
Нет нужной роли, однозначных опорных данных или обязательной revision —
`BLOCKED/PRECONDITION`; нет необходимого разрешения на изменения —
`BLOCKED/SAFETY`. Истёкшую сессию классифицируй как `BLOCKED/AUTH` и используй
[authentication.md](authentication.md), не ремонтируй из-за неё locators.

## Падение и повторный запуск

Начни с конкретной ошибки Playwright и минимального относящегося к ней evidence.

1. Исключи внешние blockers выше.
2. Найди **первую упавшую команду** в call log. Если `click` не завершился,
   изменения следующего `fill`/`Tab` не чинят этот сбой.
   `TEST`: evidence показывает ошибку TypeScript/config, неверный или
   неоднозначный locator, синхронизацию либо assertion, не выражающий критерий.
   Исправь минимально и повтори тот же шаг; максимум два безрезультатных
   исправления одной проблемы. Это относится и к навигации/locator в inspector;
   успешное исследование новой формы не считается ремонтом прежней ошибки.
3. `APPLICATION`: надёжный locator, выполненное действие и проверенные
   предусловия показывают нарушение исходного критерия. Верни
   `FAIL/APPLICATION`; не меняй приложение и не ослабляй assertion.
4. Если доказательств для различения нет либо два ремонта не помогли, верни
   `UNVERIFIED/TEST` с конкретным недостающим доказательством.

После ошибки между save и подтверждением записи сначала сверяй точный
маркер/ID предыдущей попытки. Не запускай create повторно, пока состояние
данных неизвестно. При доказанном дефекте приложения или внешнем blocker
останови repair-цикл сразу.

Повторение использует окончательный spec без правок. Для сценариев создания с `keep` сначала
`prepare`, затем `verify` читает те же ID и значения; число созданий не растёт.
В отчёте различай пройденные проверки создания/валидации и повторные проверки
сохранённых данных. Не объявляй заново пройденным сценарий, не выполнявшийся
в `verify`. При `cleanup` новый набор требует остатка общего лимита; смена run ID
его не обновляет. Прошедший тест после правки ещё не доказывает повторяемость.

При добавлении собственной логики очистки проверь её после контролируемого сбоя
на этапе, где запись уже создана, если такой прогон входит в разрешённый объём.
Запись должна быть удалена, исходная ошибка — сохранена. Учти создание в лимите.
Диагностический FAIL отчитай отдельно и убери из штатного suite.

## Артефакты и очистка

Каждому запуску, включая repair, дай отдельные outputDir и HTML outputFolder,
например `test-results/<run-id>/` и `playwright-report/<run-id>/`. Reporter не
должен стирать evidence предыдущего падения. Указывай только существующие пути.
При ручном `ELEMENT_RUN_ID` каждый раз выбирай новый ID; в команду повторного
запуска оставляй автоматическую генерацию, а не ID предыдущего запуска.

Trace и video по умолчанию выключены, в том числе у авторизованных тестов:
trace способен сохранять cookies, сетевые ответы и данные приложения.
Обычно достаточно ошибки, локального screenshot при падении и HTML report.
Если их мало, получи минимальный снимок нужного UI; trace включай лишь для
обоснованной диагностики в допускающем такую запись окружении. Не снимай
ввод секретов и не публикуй артефакты автоматически. Auth state не читается.

Если сценарий создавал данные, отчитай их из `snapshot()` общего файла задачи, включая прежние попытки:
что создано, что осталось, что не сверено и по каким точным ID. При `keep`
покажи записи для просмотра; при `cleanup` — результат каждого удаления.
Не выдай ошибку cleanup за дефект бизнес-проверки. Если cleanup был обязательным
и не завершён, общий результат не `PASS`, даже если assertions прошли.

## Короткий отчёт

Дай общий `status/reason`, затем результат каждого обязательного сценария с
кратким доказательством, пути к spec/локальному HTML report и точную команду
повторного запуска. При проблемах добавь упавшую проверку, repair с результатом,
оставшиеся записи и ограничения. Не перечисляй каждый клик.

Сверь исходные сценарии и значения с фактически выполненными. Зелёный suite
после замены ожидаемых ненулевых значений нулями, потери сценария или превышения
лимита записей не означает общий `PASS`. Skip обязательного теста
или ноль тестов не означают `PASS`, даже при exit code 0: известная внешняя
причина даёт `BLOCKED`, неизвестная/ошибка выбора тестов — `UNVERIFIED/TEST`.
Успешный repair не удаляет из отчёта исходное падение и сделанное исправление.
