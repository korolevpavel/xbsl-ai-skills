# Данные задачи и повторение

Эта справка нужна сценариям с возможным созданием записей и повторной проверке
этих данных. Самостоятельные проверки отчёта, навигации или существующей записи
не требуют добавлять prepare/verify и файл учёта созданий.

Если сценарий может создать запись, скопируй [test-data.mjs](../assets/test-data.mjs)
в consumer. Один `.test-data/<task>.json` хранит все собственные записи задачи:
основные, опорные и возможные ошибочные сохранения негативных тестов. Имя файла
и логические ключи (`document`, `client`, `missing-title`) стабильны при ремонтах;
run ID меняет только каталог артефактов. Эти имена ключей — примеры, выбери свои.
Не сбрасывай файл, лимит или ожидаемые
значения ради следующей попытки. Существующие чужие опорные записи только читай.

- `prepare` — явно выбранное создание в согласованном лимите. Перед **каждой
  возможной первой записью**, включая невалидную форму, сохрани `beginCreate(key)`.
  Неясный результат оставляет резерв до сверки UI; это защищает от дублей при
  обрыве. Новую запись нельзя начинать, пока осталась несверенная попытка.
- `verify` — режим по умолчанию: открыть известный ID и сравнить сохранённое.
  Нет файла/записи или запись пропала — `BLOCKED/PRECONDITION`, без fallback create.
  При `keep` обычная команда повторения использует этот режим. Негативный тест
  с нажатием Save относится к `prepare`, а в `verify` явно указан как не повторённый.
- `keep` сохраняет все созданные данные для просмотра; `cleanup` удаляет только
  точные свои записи в `finally`, включая исходное имя и ошибочную невалидную
  запись. Удалённые записи всё равно входят в общий лимит созданий.

API файла учёта: `record(key, values?)` задаёт неизменяемые ожидаемые значения;
`beginCreate(key)` резервирует место; `found(key, {id, url?})` сохраняет наблюдённый
ID; `absent(key)` отмечает доказанное отсутствие; `deleted(key)` — уже выполненное
удаление; `snapshot()` возвращает все записи и `budget: {created, pending, remaining}`.
Запись содержит `marker`, `values`, `status` и, после `found`, `observed.id/url`. Helper не работает с UI:
вызов `found` не заменяет проверки формы, `absent` — проверки поиска.

Пример настройки: путь, лимит `3` и режим хранения иллюстративны; подставь
согласованные параметры задачи.

```ts
import { test, expect } from '@playwright/test';
import { openTestData } from '../test-data.mjs';
import { expectAbsentBySearch } from '../checked-search.mjs';

const appURL = process.env.ELEMENT_APP_URL!;
const mode = process.env.ELEMENT_DATA_MODE ?? 'verify';
const data = openTestData('.test-data/documents.json', {
  appURL, maxCreated: 3, retention: 'keep', mode,
});
```


Маркер используй из `record`, не генерируй новый при каждом запуске. После
timeout сначала найди этот маркер/ID: одна точная запись → `found` и проверка;
доказанное отсутствие → `absent`; неоднозначность → остановка. Отсутствие не
позволяет заново создавать запись, которая уже была подтверждена созданной.
Для пустого обязательного имени заранее запиши маркер в другое поле. Если
связать запись с попыткой нельзя, проверка отсутствия/очистка остаётся недоказанной.

Первое создание явно запускается с `ELEMENT_DATA_MODE=prepare`. При `keep`
обычная команда без переменной использует `verify`: повтори её без правок spec.
При `cleanup` команда явно включает `prepare`; созданное и удалённое проверяются
внутри одного запуска. Отдельный новый набор получает новые логические ключи
в том же файле задачи и требует достаточного остатка лимита; старые ключи
сохраняются. Не запускай `verify` для уже удалённого набора.

Раздели независимые наборы на отдельные tests. Каждый из них открывает одну
известную запись; не связывай независимые сценарии через `serial`.
Если запрошена проверка обязательных полей, проверь
ошибку именно пустого поля при валидных остальных, затем отсутствие записи через
[проверенный поиск](element-ui.md#поиск-и-отсутствие). Не меняй ненулевые значения,
assertions или состав сценариев после сбоя ввода. Для RLS используй разные
contexts: владелец подтверждает существование точной записи перед проверкой
её недоступности другой роли.

Оставь обычные `.spec.ts`, копии нужных helpers и короткие команды в consumer.
Не добавляй отдельный движок запуска или восстановления.

## Новые tests с keep

Скопируй [record-checks.ts](../assets/record-checks.ts) вместе с `test-data.mjs`
и `checked-search.mjs`. Готовый helper исполняет служебный порядок: ввод и
проверка маркера → резерв → Save → список → поиск → учёт ID → проверка полей.
При ошибке он сначала сверяет попытку, сохраняя исходную ошибку. Используй его
в новых keep-сценариях создания со свободным текстовым полем маркера и доступным
списком с поиском по этому полю. Отрицательный helper дополнительно требует
отдельного наблюдаемого сообщения валидации и известной контрольной записи.
При другой структуре UI используй обычный spec с тем же учётом попыток и
проверкой идентичности; не добавляй поля, поиск или команды в приложение ради helper.
Если условия подходят, скопируй helper
без переписывания последовательности; адаптируй UI и бизнес-проверки в spec.

Ниже вымышленный пример формы. `Title`, числа, логические ключи и второй тест
не являются обязательной моделью данных или набором проверок. Включай только
сценарии из задачи и подставляй её значения.

```ts
import { checkKeptRecord, checkRejectedRecord } from '../record-checks';

const expected = { title: 'E2E document', price: 1000, quantity: 2, discount: 10 };

test('создание и сохранённые значения', async ({ page }) => {
  await checkKeptRecord({ data, key: 'document', values: expected, mode,
    ui: formUI(page) });
});

if (mode === 'prepare') test('Title обязателен при валидных остальных полях', async ({ page }) => {
  await checkRejectedRecord({ data, key: 'missing-title', values: expected, mode,
    ui: formUI(page), known: await knownControl(page), errorText: 'Title is required' });
});
```

`formUI(page)` возвращает обычные функции с locators, подтверждёнными на текущем
UI. Здесь `Title`/`Notes` — пример; выбери поля своего приложения.

| Член UI | Что реализовать в spec |
| --- | --- |
| `list()` | Открыть полный список и дождаться готовности, в том числе из формы редактирования |
| `search(query)` | Вернуть точные ID завершённой новой выдачи по [примеру поиска](element-ui.md#поиск-и-отсутствие) |
| `newRecord()` | Открыть новую форму и дождаться содержимого |
| `fill(values)` | Заполнить поля значениями согласованного сценария |
| `marker` | Locator независимого текстового поля, например Notes; helper сам вводит и проверяет UUID |
| `save(validationText?)` | Команда Save и ожидание нового исхода; используй `saveWithFeedback` ниже, когда UI даёт отдельные признаки успеха и ошибки |
| `open(id)` | Открыть единственную запись с точным ID из текущего списка |
| `assertSaved(values)` | Сравнить проверяемые значения после открытия; вычисления проверять, если они входят в задачу; маркер helper проверяет сам |
| `makeInvalid()` | Нарушить только проверяемое правило, например очистить одно обязательное поле |
| `rejection` | Locator наблюдаемого сообщения об ошибке этого поля |

Для формы, которая после сохранения возвращается в список, возьми готовое
ожидание из того же файла. Укажи реально наблюдённые признаки:

```ts
import { saveWithFeedback } from '../record-checks';
// Внутри formUI(page):
save: validationText => saveWithFeedback({
  button: page.getByRole('button', { name: 'Save', exact: true }),
  saved: page.getByRole('heading', { name: 'Documents', exact: true }),
  error: page.getByRole('alert'),
  validationText,
}),
```

`saved` должен появляться только после действия. Заголовок открытой формы,
видимый до Save, не доказывает его завершения: ранний Close гоняется с сохранением,
а ошибка сервера остаётся незамеченной. `saveWithFeedback` отвергает такой старый
признак, ждёт новый исход и бросает ошибку для неожиданного сообщения. Негативный
helper сам передаёт точный `validationText`; в положительном ошибку не допускает.
Если таких UI-признаков нет, реализуй `save` через наблюдённый ответ UI-запроса
и фактическое состояние формы. Не угадывай endpoint и не выдавай HTTP 5xx за успех.

`knownControl` читает существующие ID и маркер **того же поля**: результат
`{id, marker}` используется для проверки поиска. `errorText` — конкретная
наблюдённая ошибка поля, не общий `/required/` и не видимость пустого alert.
`fill` и `assertSaved` не меняют независимое поле маркера; если пользователь
проверяет Notes, выбери другое доступное поле или адаптируй идентификацию.
Если свободного поля нет, сохрани допустимый уникальный признак в `record.values`
и реализуй тот же порядок обычным spec: UUID не подходит, например, числовому ИНН.
Недоказанная идентичность не позволяет автоматически повторять Save.

В `verify` негативный Save не выполняется и не объявляется повторно пройденным.
Список оставленных записей бери из `data.snapshot()`, включая ранние попытки.
Оставшийся pending означает несверенные данные этой задачи: общий PASS не доказан.

Проверь окончательный prepare на новом разрешённом наборе, если после первого
Save менялся код сценария: успешное продолжение старой pending-попытки не
доказывает первый запуск. Используй новые логические ключи в том же файле и
остаток лимита, не сбрасывай данные. Если лимита не хватает, отчитай это ограничение.
